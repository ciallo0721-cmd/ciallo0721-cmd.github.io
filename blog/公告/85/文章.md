# 博客架构升级：从 articles-data.js 到 CWBI

==博客的元数据层升级了。以前所有文章的标题、摘要、标签都挤在一个巨大的 articles-data.js 里，现在每篇文章多了一个随文章走的 .cwb 文件，首页优先读 CWBI 数据源，旧 JS 数据降级为兜底。这篇文章把整套设计讲清楚。==

## 一、旧架构的问题：一个越滚越大的 JS 文件

升级前，博客的元数据全靠根目录的 articles-data.js。它是一个 JS 对象字面量，每篇文章一条记录，大概长这样：

```js
window.articlesData = {
    articles: [
        {
            id: 1,
            category: "教程",
            fileName: "教程/1/",
            title: "UTAU教程：从调音到发布完全指南",
            excerpt: "...",
            date: "2025-12-28",
            tags: ["UTAU", "虚拟歌姬", "调音"],
            readTime: 15,
            featured: true
        },
        // ... 后面还有 80 条
    ]
};
```

用久了问题很明显：

**数据和代码耦合。** 它是 JS 语法，不是纯数据。别的语言想读它，要么正则硬抠，要么像 CWBI转换器.py 现在做的那样——先把 node 拉进来求值一遍再 dump 成 JSON。一个「数据文件」居然依赖一个 JS 运行时才能解析，这不合理。

**元数据不跟着文章走。** 文章本体在 blog/分类/id/ 目录里，元数据却在根目录一个大文件里。想把某篇文章整个拷走备份，还得回大文件里把对应那条挖出来。

**单文件越滚越大，谁都不敢动。** 80 多条记录挤在一个文件里，任何一次批量编辑都是高风险操作，一条逗号写错整个首页的渲染就挂了。

**文章页不知道自己是谁。** 打开 blog/心理学/23/ 这个页面，页面自己的元数据（作者、日期、标签）不在页面旁边，而是要回根目录去查。文章页无法独立地展示自己的信息。

## 二、CWBI 是什么

CWBI 全称 **CialloWebBlogInformation**，是这个博客自己的文章元数据格式与读取体系。核心思路一句话：

==把元数据从中心化的大文件里拆出来，一份 .cwb 文件跟着一篇文章走，首页通过清单文件发现它们。==

整套体系由五部分组成：

| 组件 | 位置 | 职责 |
|------|------|------|
| .cwb 文件 | blog/分类/id/id.cwb | 单篇文章的元数据（格式见下节） |
| cwb-manifest.json | 站点根目录 | 全站文章的 .cwb 发现清单 |
| cwbi.js | js/js/cwbi.js | 核心解析器：解析 .cwb + 加载清单 |
| cwbiblog.js | js/js/cwbiblog.js | 文章页侧脚本：页面内读取自己的 .cwb |
| CWBI转换器.py | 实用工具/CWBI转换器.py | 生成管线：从 articles-data.js 批量生成 .cwb |

名字里的「I」取自 Information——每个 .cwb 本质上就是一篇文章的「信息卡」。

## 三、.cwb 格式详解

.cwb 是一种类 JSON 的自定义格式，但比 JSON 更宽松：支持 // 注释、True/False 布尔字面量、逗号分隔的字符串数组，整个文件按「块」组织。真实样例（blog/教程/1/1.cwb）：

```
// CWBI 文章信息文件 · 由 实用工具/CWBI转换器.py 生成 · 手动编辑请保留格式
// 文章 #1
[
    {
    index:
        "title"="UTAU教程：从调音到发布完全指南" //标题
        "author"="ciallo0721-cmd" //作者
        "date"="2025-12-28" //日期
        "tag"="UTAU","虚拟歌姬","调音" //标签
        "excerpt"="学习如何使用UTAU进行歌声合成……" //摘要(扩展字段)
        "readTime"=15 //预计阅读分钟(扩展字段)
        "featured"=True //精选(扩展字段)
    }
    {
    is?:
        "isadult"=False //轻度或重度成人
        "istop"=False //置顶
        "isPsychology"=False //心理学
        "isMedical"=False //医学
        "isOpposition"=False //有争议的
        "istest"=False //测试文章(不显示在首页或blog页)
        "isCopyProtection"=False //有版权保护
        "isAIGC"=False //完全AI生成且未查资料
        "isiframe"=False //使用iframe
        "isuseArticleEditor.py"=True //使用了文章编辑器
        "canCompatible"=True //兼容旧版文章data
    }
    {
    html:
        "path"="blog/教程/1"
        "html"="index.html"
    }
]
```

三个块各管一摊：

**index: 块** —— 基础信息。标题、作者、日期、标签，外加三个扩展字段（excerpt / readTime / featured），向后兼容 articles-data.js 里的同名键。

**is?: 块** —— 布尔标记位。这一块是给未来留的扩展空间：置顶、成人内容标记、心理学/医学分类标记、版权保护、是否测试文章……全部是开关式的 flag。首页读取时，istest=true 的文章会直接被过滤掉，不进列表。

**html: 块** —— 指路。path + 文件名，解析器靠它把 .cwb 还原成一个和旧版 articlesData 完全同构的文章对象。

为什么不用 JSON？因为注释。元数据文件里放行内注释，每个字段后面直接写它是干嘛的，人肉编辑的时候不用来回查文档——这是 .cwb 相对 JSON 最实际的取舍。

## 四、生成管线：CWBI转换器.py

.cwb 不手写。实用工具/CWBI转换器.py 负责批量生成，在仓库根目录跑：

```
python "实用工具/CWBI转换器.py"            # 生成全部 .cwb + cwb-manifest.json
python "实用工具/CWBI转换器.py" --inject   # 额外给文章页注入 cwbiblog.js 标签
```

它做三件事：

1. 用 node 把 articles-data.js 求值成 JSON（对，旧数据文件还得靠 node 读，这正是要淘汰它的原因之一——过渡期它还是唯一的事实来源）；
2. 逐篇生成 blog/分类/id/id.cwb，目录不存在就跳过；
3. 汇总生成根目录的 cwb-manifest.json，里面是全站 .cwb 的路径清单。

--inject 是幂等的：给每个文章页的 </body> 前注入一行 cwbiblog.js 的 script 标签，已有的自动跳过。

==所以现在的发文章流程变成了两步：文章编辑器.py 导出 → 再跑一遍 CWBI转换器.py。漏了第二步的话，.cwb 会停留在旧内容，首页卡片显示过期信息，而文章页本身是对的——特别容易漏。==

## 五、前端读取：cwbi.js 解析器

js/js/cwbi.js 是 CWBI 的核心解析器，无依赖，干四件事：

**解析 .cwb。** 先做一次字符级扫描去掉 // 注释——注意要跳过引号内的 //，免得把正文里的 URL 误杀。然后逐行匹配两种结构：块头（index: / is?: / html:）和键值行（"key"=value）。值解析也做了类型推断：true/false 转布尔、纯数字转数值、单个引号串转字符串、逗号分隔的多个引号串转数组。

**转兼容对象。** toArticle() 把解析结果还原成和旧版 articlesData 完全同构的对象（id / category / fileName / title / excerpt……），外加 CWBI 专属的 flags 字段。这样下游渲染代码完全不用改。

**加载清单。** fetch cwb-manifest.json 拿到全站清单，然后按每批 8 个限流并发拉取所有 .cwb（本地 http.server 并发太大会拒连），失败自动重试一次。

**双源合并。** mergeArticles() 把 CWBI 列表和旧版 articlesData 列表合并：同 id 的 .cwb 覆盖 JS 数据，CWBI 拉不到的靠旧数据兜底，最后按日期倒序 + id 倒序排好。

## 六、接入方式：双源合并，渐进升级

blog/index.html 的接入策略是「新旧并存，CWBI 优先」：

- 先按老路子加载 articlesData，保证基础渲染永远有数据；
- 再调 CWBI.loadAll() 拉全部 .cwb（设了 2.5 秒超时，超时或失败就直接用旧数据渲染，首页绝不白屏）；
- 拉取成功后 mergeArticles 合并，.cwb 数据覆盖同 id 的旧数据。

文章页侧是另一个脚本 cwbiblog.js：它从 URL 推断出文章 id，然后 fetch 同目录的 id.cwb 解析，把作者、日期、标签填进页面预留的 #cwbi-meta 容器。失败静默降级，不中断页面。

这样升级的好处是==可以随时回滚==：把 cwbi.js 那行引用删掉，博客立刻回到纯 articles-data.js 时代，一根毛都不少。反过来，等哪天 articles-data.js 彻底退役，删掉兜底分支就行，.cwb 本身已经是完整的数据源。

## 七、这套设计换来了什么

**数据跟着文章走。** 拷走 blog/心理学/23/ 一个文件夹，元数据就全在里面，不再依赖根目录的大文件。

**文章页自治。** 每个页面通过 cwbiblog.js 就地读自己的元数据，填自己的信息栏，不需要回根目录查询。

**非 JS 生态可读。** .cwb 格式足够简单（去注释 + 逐行匹配键值），Python 端处理起来毫无压力，不用再拉 node 求值。

**flag 系统留足扩展空间。** is?: 块里的十几个开关，置顶、内容分级、争议标记、测试文章过滤……都是加一个字段名就能启用的能力，格式不用动。

**渐进迁移零风险。** 双源合并 + canCompatible 标记，旧数据兜底，CWBI 优先覆盖，两边永远不会打架。

## 八、写在最后

这次升级没有推倒重来——articles-data.js 还在，还是过渡期的事实来源，CWBI 是叠在它上面的一层新数据面。等 .cwb 覆盖稳定后，旧文件会功成身退。

对写文章的工作流来说，变化只有一条：**导出之后记得跑一遍 CWBI转换器.py**，不然首页卡片会活在旧时间里。
